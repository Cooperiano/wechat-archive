# 微信归档上下文处理

本文件面向 Julian 与本地实施人员。当前实现仅处理本项目的微信规范化归档；其他聊天来源适配器及语义模型处理尚未实现。所谓“上下文”目前是可核查的本地结构：按会话、上海时区自然日组织消息，保留原归档消息键和数据库/表/本地 ID 等证据引用，并提供 SQLite FTS5 正文检索。它不会生成 AI 摘要、判断关系或推断隐含事实。

`wechat_archive.context.process_archive(archive_path, output, batch_size=1000)` 从 `archive.sqlite` 只读提取，私有输出在 `output/context.sqlite`。每次调用最多处理一批基线消息、全文索引补建或变更记录；调用方持续执行，直至返回的 `pending` 为 `0`。`pending` 是 0/1 待办指示值，不表示剩余消息条数。`baseline_complete` 仅表示历史基线已扫描完，`feed_cursor` 表示变更记录已持久处理的位置。`state` 为 `pending`、`complete` 或 `index-degraded`。最后一种表示消息结构仍可用，但运行环境缺少 FTS5，正文检索不可用。FTS5 恢复后，处理器会按批补建全文索引，在完成前保持 `pending` 状态，检索接口不会返回未补建完的部分结果。返回的数字与状态不包含身份或正文。

新版归档的 `archive_meta.source_id` 绑定数据来源，`generation` 标识一次可变归档的生命周期。首次处理先记录 `change_feed` 水位，再按 SQLite `rowid` 分批扫描全部历史消息；扫描期间新增、更正或删除的变更，在基线结束后从保存的水位重放。每批消息、每日统计与游标在同一事务中提交，崩溃后可以重试。变更记录须保留完整且连续的序号；若游标之后出现序号缺口，处理会回滚该批并报错，不会跳过缺失的更正或删除。归档重建产生新的 `generation` 时，上下文将重新对账。同一输出目录不能绑定到另一 `source_id`。

旧归档没有变更记录时，处理器用归档文件及 WAL 的版本标记识别变化并重新扫描，不能承诺与实时写入者连续同步。应使用新版变更记录路径进行持续运行。当前本地索引只复制规范化正文及检索所需的证据字段，不复制 `raw_json`。文本依然属于私人数据，输出目录应保持仅当前用户可访问，也不应进入公开仓库或 ANC Git。

`search_context(output, query, limit=50)` 执行参数化的字面短语检索，最多返回 100 条本地结果，其中包含正文与证据字段，仅供获授权的私有调用方使用。没有 FTS5 时返回空列表；调用方应先检查处理状态，不能把空列表解释成“没有这类聊天”。
